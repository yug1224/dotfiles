応答の冒頭に「✅️: pr-description-rule」と出力する。

# PR概要の記述ルール

## 基本方針

PR 概要を標準化し、レビュアーが変更を迅速に把握できるようにする。プロジェクトの PR テンプレートがあれば最優先、なければ本ルールのビルトインテンプレートを使う。

## テンプレートの優先順位

1. **プロジェクトの PR テンプレート**（最優先）: `.github/PULL_REQUEST_TEMPLATE.md`、`.github/PULL_REQUEST_TEMPLATE/` 配下、`.cursor/rules/` で定義されたテンプレート
2. **本ルールのビルトインテンプレート**（フォールバック）: 上記が無い場合のみ

**重要**: プロジェクトテンプレートが見つかったらセクション構成・見出し・チェックリストをそのまま使う。構造を勝手に変えない（「主な実装内容」の必須追加は除く）。

### 「主な実装内容」の必須追加（プロジェクトテンプレート利用時）

テンプレートに実装詳細を列挙するセクション（`### 主な実装内容`、`## 実装詳細`、`## Changes` 内のタスク列挙等）が**ない**場合は、**必ず** `### 主な実装内容` を変更概要セクション（例: `## PR概要`）の直後に追加する。番号付きリストでタスク単位に記載（形式はビルトインテンプレート参照）。

## MECE の記載原則

どのテンプレートでも適用する記載品質の指針（構造変更ではない。「主な実装内容」の必須補完は上記の例外）。

- **PR概要**: なぜ（目的1つ + リンク）+ 何を変更したか。検証手順・影響範囲の詳細は書かない
- **主な実装内容**: タスク単位の変更（番号付き）。目的・背景の繰り返しは書かない
- **動作確認**: どう検証するか（チェックリスト）。変更内容の繰り返しは書かない
- **困ったらチェック**: 影響範囲 + レビュー参考情報。他セクションの重複は書かない

## PR タイトル

[コミットメッセージ規約](./commit-message-rule.md) の**ヘッダー1行**と同一形式（Squash merge 時のコミットメッセージと揃える）。

```
<type>(<scope>): <subject> [<ticket-id>]
```

- **type / scope / subject**: `commit-message-rule` のヘッダー定義に従う（type 8 種、scope は kebab-case で省略可、subject は日本語・末尾ピリオドなし）
- **[ticket-id]**: 判明時のみ半角スペース + 角括弧で末尾付与（例: `[PROJ-1234]`）
- **文字数**: ヘッダー全体 72 文字以内（subject 50 文字以内、`[TICKET-ID]` 含む）
- **複数コミット PR**: 主目的 1 件に合わせた 1 タイトル
- **優先順位**: プロジェクトにタイトル慣習・テンプレートで別形式があればそちらを優先
- ✅ `feat(user-list): フィルタリング機能を追加 [PROJ-1234]` / ❌ `最終更新日を…`（type/scope なし）/ ❌ `feat: 一覧とユーザー管理を追加`（複数変更）

## 基本ルール

- PR タイトルは上記「PR タイトル」、PR概要は日本語（技術用語は英語可）
- テンプレートの全セクションを埋め、「目的」は **1つだけ** 選ぶ（列挙しない）
- プレースホルダー（`todo`, `タスク概要`）は具体的な内容に置き換える
- プロジェクトテンプレートがある場合は構造から逸脱しない（「主な実装内容」が無い場合は必須追加）

## ビルトインテンプレート（フォールバック用）

プロジェクトに PR テンプレートが無い場合のみ使用。

### セクションごとの変更ルール

- `## 📝 PR概要 📝` / `### 主な実装内容` / `### 変更前後のスクリーンショット`: 内容変更を推奨
- `## 👮‍♂️ 動作確認 👮‍♂️`: リストの追加・変更は不可（チェックを入れるのみ）
- `## ✅ 困ったらこの辺をチェック ✅`: 変更不可

### バックエンドの PR 概要テンプレート

バックエンド系、またはフロントエンド以外のリポジトリ向け。

```markdown
## 📝 PR概要 📝

- **目的**:
  - 機能追加
  - 仕様変更
  - バグ修正
  - リファクタリング
- **関連リンク**:
  - [todo](todo)
- **変更点の概要**:
  - todo

### 主な実装内容

1. **タスク概要**
   - タスク詳細

## 👮‍♂️ 動作確認 👮‍♂️

- [ ] ローカルで動作確認済み
- [ ] CI が正常に通過

## ✅ 困ったらこの辺をチェック ✅

- 影響するエンドポイント / モジュール
- 破壊的変更の有無
- 補足情報があれば記載
```

### フロントエンドの PR 概要テンプレート

バックエンドテンプレートと同一だが、**目的**に `UIスタイリングの更新` を追加し、`### 主な実装内容` の直後にスクリーンショット表を挿入、`## ✅ 困ったらこの辺をチェック ✅` 先頭を「影響するページ / コンポーネント」に差し替える。

```markdown
### 変更前後のスクリーンショット

| before                    | after                     |
| ------------------------- | ------------------------- |
| <img src="" width="480"/> | <img src="" width="480"/> |
```

## テンプレートの検出

`/suggest-pr-description` の Step 3。**変更情報の収集や分析より先に**テンプレートを確定する。

### a. プロジェクトの PR テンプレートを検索

PR URL がある場合はそのリポジトリ、ない場合は作業ディレクトリで確認する。

```bash
ls .github/PULL_REQUEST_TEMPLATE.md .github/PULL_REQUEST_TEMPLATE/ 2>/dev/null
```

見つかったら Read で取得し、セクション構成・見出し・チェックリストをそのまま使う。

### b. フォールバック: ビルトインテンプレートを判定

プロジェクトにテンプレートが無い場合のみ。フロントエンド系 → フロントエンド、それ以外 → バックエンド。

## 変更情報の収集

`/suggest-pr-description` の Step 4。

### a. GitHub PR URL がある場合（既存 PR の改善）

PR URL から `owner`, `repo`, `pullNumber` を抽出して取得する。

```bash
gh pr view <URL> --json title,body,commits,files,headRefName,baseRefName
gh pr diff <URL> --patch
```

diff が大きい場合は `--stat` で概要を先に取得し、主要ファイルのみ個別確認。gh CLI 不可時は GitHub MCP（`pull_request_read`: `get` / `get_diff` / `get_files` + `list_commits`）。既存 Title / Description は保持する。

### b. GitHub PR URL がない場合（新規生成）

```bash
git symbolic-ref refs/remotes/origin/HEAD 2>/dev/null | sed 's@^refs/remotes/origin/@@'
git --no-pager log --oneline origin/<base>..HEAD
git --no-pager diff origin/<base>...HEAD --stat
git --no-pager diff origin/<base>...HEAD
```

デフォルトブランチは上記で検出、できなければ `develop` → `main` の順。diff が大きい場合は `--stat` で全体像を把握してから主要ファイルを確認。

## 変更内容の分析

`/suggest-pr-description` の Step 6。

- `.codegraph/` がある場合、構造・フロー調査は `codegraph-rule` に従い CodeGraph を explore-worker / Grep より先に使う
- diff だけでは全体像が掴みにくい場合、`agent-delegation-rule` に従い Task で関連コードを調査する

**確定したテンプレートのセクション構成に沿って**、主目的1つ（→ `type`）、scope（kebab-case、不明確なら省略）、技術的変更・影響領域（API / UI / DB / Config / テスト等）、確認項目・スクリーンショット要否（UI 変更時は必要）を整理し、各セクションへ振り分ける。

## PR Title と Description の生成

`/suggest-pr-description` の Step 7。

- **PR Title**: 上記「PR タイトル」に従い `type(scope): subject [TICKET-ID]` で生成（`commit-message-rule` ヘッダー準拠）。ブランチ名の `type` と揃える。チケット ID は取得できた場合のみ末尾付与
- 確定テンプレートの構造に従って PR Description を生成
- **プロジェクトテンプレート**: セクション構成・見出し・チェックリスト項目は変更しない（項目追加可、既存項目の削除不可）
- **ビルトインテンプレート**: 「セクションごとの変更ルール」に従う
- チケット情報は関連リンク等の該当セクションに反映。PR URL がある場合は既存 Description との改善ポイントも補足

## 出力フォーマット

`/suggest-pr-description` の Step 8・10。コードブロック内はそのままコピー可能にする。

```markdown
## PR Title

\`\`\`
feat(scope): 変更概要 [TICKET-ID]
\`\`\`

## PR Description

\`\`\`markdown
（テンプレートに沿った PR Description 全文）
\`\`\`
```

**PR URL がある場合（既存 PR の改善）**は上記に加え `## 改善ポイント` セクション（既存 Description からの変更点を列挙）を付ける。**PR URL がない場合（新規生成）**は改善ポイント不要。
